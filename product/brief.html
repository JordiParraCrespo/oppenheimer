A terminal and VM orchestrator you log in to from anywhere

Open a browser, pick a machine you own or a fresh VM, get a terminal that survives everything, type claude or codex. Run thirty of them. That is the product. This brief records what we learned from OpenClaw and Orca, the architecture that follows, and what to build first.

Thesis

Do not build an agent framework. Build a thin product over agents we do not own. The unit of the product is a real PTY on a real machine, shown in a browser. Every coding agent that runs in a terminal is supported by construction, with zero adapters.

The platform owns three things: the terminal experience, the fleet of machines and workspaces, and the board that shows what every session is doing. It does not own the agent loop, the model credential, or a plugin marketplace.

Software development only for the MVP. Other verticals wait until the core loop is boring.

What OpenClaw and Orca taught us

Rejected · OpenClaw

A framework for a different problem

  • Always-on personal assistant: gateway, 15+ chat channels, memory, skills marketplace, all in one process. Four days lost just building it.
  • A published security analysis found trust scattered across layers, exec allowlists bypassable by shell parsing, and an unverified skill supply chain.
  • Nothing can be adopted piecemeal. That is what "too large" costs.
Reference · Orca

A cockpit around unmodified agents

  • Electron app. Runs Claude Code, Codex, and 25+ CLIs in parallel git worktrees. Wraps the environment, never the agent.
  • Bring your own subscription. No proxy through the vendor.
  • First commit March 2026, 50k+ stars by August. The shape is right.
  • Limit for us: state lives on one laptop, remote is SSH only, no sandboxes, no scoped secrets.

How Orca's remote terminal actually works

The smoothness does not come from the widget. It comes from who owns the PTY.

Renderer

  • xterm.js with the WebGL addon, plus fit and search. GPU rendering keeps noisy builds from stalling the tab.
  • Only the active worktree's terminals are mounted. Idle ones are "cold parked", so a fleet of thirty sessions does not cost thirty live renderers.

The relay daemon

  • On first connect Orca uploads a small Node package to the host over SSH and launches it. Everything after that goes through the relay.
  • JSON-RPC 2.0 with notifications, multiplexed over one SSH channel. PTY bytes, git, filesystem, and port scanning share it.
  • The relay spawns PTYs with node-pty and keeps a recent-output buffer per PTY, so a reconnecting pane replays the tail instead of going blank.
  • PTYs belong to the daemon, not to the SSH session. When the link drops, the daemon holds them for a grace period and reattaches over a Unix socket. Closing the laptop does not kill the agent.
  • Reconnect is a state machine with an exponential backoff ladder.
Their two pain points: node-pty is native and fails to compile on hosts without a C++ toolchain, and most open bugs live in the reconnect path. We ship prebuilt binaries and treat reconnect as the feature that gets the most tests.

Architecture

A browser cannot SSH, so the topology inverts. Each machine runs a runner daemon that dials out to the control plane. The Mac Studio behind a home router and the server in a datacenter are the same case: no inbound ports, no SSH key distribution.

Runners connect out, so the control plane never needs to reach a target. The browser never talks to a target directly.

What makes it feel local

Two target modes

A target is any machine the runner daemon is installed on. It registers in one of two modes, and a project can use both. The browser sees the same thing either way: a session with a PTY, a file tree, a diff, and a git remote. The mode only changes what the runner does before it opens the PTY.

Mode A · Direct machine

Full access, local or remote

  • Runner runs as you on a machine you own: laptop, Mac Studio, bare server. Sessions are PTYs in a worktree under a path you pick.
  • No isolation beyond worktrees. The agent sees your home, toolchains, docker socket, and logged-in CLIs. This is Orca over SSH, and the right default for a box that is yours alone.
  • Local and remote are the same to the platform. The runner dials out either way.
  • One install command. launchd on macOS, a systemd user unit on Linux, so it survives reboots.
Mode B · Isolated VM

Fresh VM per task, Docker inside

  • Runner acts as a provisioner on a hypervisor host. Each task gets a VM with 4 to 8 GB RAM and 2 to 4 vCPUs, Docker preinstalled, the repo cloned at the requested branch.
  • The setup script runs inside the VM, then the PTY opens inside it. The agent can bring up Postgres or Redis for the task without touching the host.
  • Created on session start, paused when idle, destroyed after retention. A persistent per-target home volume keeps claude logged in across fresh VMs.
  • Linux host: Firecracker microVM. macOS host: Apple Virtualization via tart. Cloud: a provider adapter instead of a daemon.

Order: mode A on day one, since it is the terminal from the section above. Mode B after secrets, starting with Linux and Firecracker because the images are reusable for the cloud adapter later. macOS VM hosting after that.

Multiple accounts per provider

Orca lets one person hold several Claude, Codex, Kimi, OpenCode, Gemini, and MiniMax accounts, switch in one click, and see usage per account. It does this without ever holding a credential, and the mechanism maps directly onto what the platform already has.

Orca · discovery and hot-swap

A viewer over files the CLI owns

  • Log in to each account from a terminal once. Orca scans ~/.claude, ~/.codex and friends, and you label what it finds.
  • Each managed account gets a runtime home. New sessions launch with the CLI's config-dir variable pointing at the active one. Running sessions keep their account until restart.
  • The user's real config is mirrored into every account home, so hooks and MCP servers follow the person, not the account. On Codex it also maintains trusted_hash entries so its status hooks are trusted.
  • A guard stops two sessions from refreshing the same token at once.
Orca · usage meters

No API calls, no extra auth

  • Reads the usage state each CLI keeps on disk. Shows plan, 5-hour, daily, and weekly windows with reset times, and warns at 80 percent.
  • Status bar follows the active account. The popover lists every provider and account with independent bars. The mobile app has the same switcher.
  • Numbers lag by one turn because they update when the agent writes its file. Cost estimates come from a local pricing table and are labelled as not authoritative.

macOS is resolved. Since Claude Code 2.1.144 the Keychain entry is keyed to CLAUDE_CONFIG_DIR, so two config dirs are two independent logins on one Mac. Yes, you log in once per machine per account. A credential is issued to a CLI on a machine, and Orca's own instruction is "log in from a terminal at least once" on each one. The platform makes it a thirty-second two-click flow with a login button, keeps accounts on the persistent home volume so a fleet of VMs counts as one machine, and flags needs-login and expired on the board. For unattended machines where nobody will click, Claude Code's documented path is claude setup-token, a one-year subscription token meant for CI, stored in the vault and injected per session like any secret.

Decided: one button, Continue with GitHub. Connecting machines and provisioning VMs

Three projects each solve one slice of this well. herdr for owning terminals on many machines, the GitHub Actions runner for registering machines behind firewalls, Actuated for a Firecracker VM per job on hosts you own.

herdr · take the state detection

Server owns the PTY, client only renders

  • One Rust binary, client and server. Remote machines are SSH to a herdr server on the remote, each with independent reconnect.
  • Pane state from two layers: the foreground process, plus "screen manifests" that match the bottom of the live screen. Every pane is working, blocked, done, idle, or unknown. No agent integration needed.
  • After a restart, processes die but agents resume by their native session id. Scrollback is not persisted by default because it holds secrets.
  • Socket API with wait conditions: prompt an agent and block until it is settled. That is the delegation primitive.
Actions runner · take the registration

Registration token, keypair, outbound only

  • UI shows a one-hour registration token embedded in an install command. The runner generates an RSA keypair, sends the public key, gets a clientId. The user's credentials never touch the machine.
  • Every boot: sign a JWT with the private key, exchange for a short-lived session token, open an outbound connection and wait for work.
  • Per job: a token scoped to that job, lifetime of the job plus ten minutes, delivered encrypted to the runner's public key, held in env only, scrubbed from logs.
  • Two flavors: persistent (our direct machines) and ephemeral just-in-time (the identity a fresh VM gets).

Actuated: what running Firecracker per job taught them

  • Agent on the host, one single-tenant microVM per job, immutable rootfs with Docker already running, VM deleted when the job exits. Boot to ready in one to two seconds.
  • Images are 80/20. A lean Dockerfile with common toolchains beats replicating GitHub's 3,000-package image.
  • The VM is fast and everything around it is slow: webhook delivery, API limits, DNS on the host. Design for missing and out-of-order events. Run a registry pull-through cache on the host.
  • Autoscaling was hard because they could not predict which VM gets which job. We sidestep it: the scheduler picks the target before the VM exists, so there is no pool to size.

Service decomposition

Turborepo, yes. Microservices on day one, no. Split by package boundary now and by process later. The control plane is one Node process with identity, fleet, scheduler, relay, vault, and events as modules behind interfaces. The relay is the first to split out, because it is stateless, bandwidth-heavy, and the only piece that benefits from running close to the targets.

One change from the earlier stack: the runner should be Go, not Node. Everything here that runs on other people's machines is a single static binary. node-pty's native build is Orca's top install complaint, and a Firecracker, vsock, and tap orchestrator in Node fights the language. Go has first-class Firecracker, vsock, and netlink libraries and cross-compiles to every target. Web and control plane stay TypeScript, and the protocol package becomes the contract between the two languages.

Security review

Assets in order of how bad losing them is: vendor subscription logins on targets, GitHub access, project secrets, the targets themselves, code and scrollback, the control plane database. The attacker that matters most is the agent itself, steered by a README, an issue, or a dependency. Everything below is the same set of controls Claude Code on the web, the Actions runner, and Actuated already run.

Tailscale as the perimeter

Wanted, not mandatory, so it is a layer that switches on without changing the design. Both the control plane and the Go runner embed Tailscale as a library. With a flag and an auth key they listen only on the tailnet. Without it, they listen normally behind whatever reverse proxy you have. Same binary, two modes.

The MVP: Orca on the web, no virtual machines

In one line: connect a host you own, then run sessions on it with a coding agent from the catalog, or a blank terminal. The agents are listed in versions/mvp/00-scope.md. One user, hosts in direct mode only, every session a git worktree plus a tmux terminal streamed to the browser. The control plane is hosted and fully web based. The Create session screen is the product. The sidebar lists sessions. No VMs, no sleep tiers, no accounts model, no enterprise layer. Those are the slices after.

Reset on 2026-09-12. The earlier MVP (sessions in KVM guests on the runner host, Codex first) is kept in the notes as history. The in-depth design now lives in product/versions/mvp/, one document per area, starting with 00-scope.md.

You tap Continue with GitHub and pick the repositories the app may see. Onboarding hands you one install command to paste on the Hetzner box or the Mac Studio; the host appears. New session, four chips: host optimus, repo xrp-mobile, branch main, agent Claude Code. Go. The runner fetches main, adds a worktree, opens a tmux window in it, runs claude. If that host has never seen your account, the login URL becomes a button. You give the task and close the phone. On the laptop it is still there. You open three more and switch in the sidebar.

Sleep, wake, and what it costs

Yes, sessions can sleep and wake like a Claude Code on the web session that expires and comes back. On our own KVM host it is better, because there are two kinds of sleep and we get both.

Suspend · like closing a laptop lid
  • libvirt managedsave: guest memory to a file on the host, VM stops, RAM and VM slot freed
  • Everything survives: the agent mid-task, tmux, scrollback, open files
  • Wake in a few seconds from NVMe, cursor where it was
  • Costs disk for the memory image, up to 8 GB
Hibernate · like environment expired
  • VM destroyed, overlay and account volume kept
  • Working tree, uncommitted changes, and login survive; processes do not
  • Wake by booting the existing overlay, relaunching tmux, resuming the agent by its session id, showing the old scrollback tail
  • Costs disk for the overlay only
watchDisks must not change while suspended. Tokens expire while asleep, so the runner mints and rotates a fresh one before announcing ready. The guest clock jumps, so chrony is in the image. Agent session ids are captured continuously, not at sleep time. this hostThe MVP host is an i7-6700 with 4 cores and 8 threads, 64 GB, two 512 GB SATA SSDs, about €63 a month. RAM-rich, CPU-poor. So the tiers use RAM first: two sessions running, up to five more paused in RAM with instant wake, ten more suspended on disk with a fifteen-second wake, dozens hibernated. The two-VM cap is correct for this CPU. Build the MVP on it, then move to an AX42 or AX52 class host: 8 cores and NVMe give four to six running slots and a three-second suspend wake for the same money or less. Account volumes and hibernated overlays copy across as files. pricingCompute is the user's host, so the product charges for the console: a flat personal plan. Hosted hosts later at pass-through plus margin or per running-VM-hour. One rule fixed now: sleeping sessions are free, because they cost disk only. cloudsThe same tiers map onto provider operations. AWS EC2 has native hibernation with RAM saved to the encrypted root volume and costs only EBS while asleep, about $5 a month for our shape. GCP suspends natively, Azure hibernates. Fly Machines have no suspend but stop and start in seconds for cents. Hetzner Cloud bills a stopped server at full price, so hibernate there means snapshot and delete, and wake takes minutes. Cloud sessions bill per running hour plus storage while asleep at provider price plus margin. AWS adapter first, Fly second, after the MVP. versusFor two sessions running six hours a day and ten asleep: an AX42 host is €47 to €57 flat with sleeping free. Compute is one to five percent of a task, never the reason to change the architecture. VMs stay for isolation, Docker inside, and the day a second person shows up. Lessons from a reconstructed desktop agent app

A reverse-engineered Electron app whose desktop asks a broker for a persistent remote box, then talks HTTP with bearer tokens to a gateway and an exec daemon inside it. The connection itself is unremarkable. The operational layer around it is what a product like this spends its second year on, and it is worth copying.

Take
  • A brokered descriptor with structured hints: blocked with retry-after, update required. Our session attach ticket carries the same.
  • Migration as a phased, resumable stream with offset keys, 3-second reconnects, 30-second stall detection, and a remembered terminal event. For host moves, image updates, and hibernate-to-wake progress.
  • Update equals recreate with data preserved. Workspace VMs get new golden images that way, keeping worktrees and account volumes.
  • Disk-pressure guard surfaced as a status event. Epoch counter so a late reconnect cannot clobber a newer one.
  • Background terminals persisted as text files with frontmatter and an exit footer, the format for archived scrollback.
Leave
  • Pipes instead of a PTY. Its agents read command output as text; ours get a terminal. That is the product difference.
  • One forever box per user. We have a workspace VM per repo plus clean VMs.
  • VNC inside the box for computer use. On the Mac Studio the agent drives the simulator directly.
  • An egress tunnel through the user's desktop. The tailnet gives that as a firewall rule.
  • A gateway of 34 plugin extensions. The OpenClaw shape again.

Lessons from herdr

herdr is the closest thing to this product that exists: a Rust terminal workspace manager for coding agents, with a background server, panes marked working, blocked or idle, and machines reachable over SSH. Its source was read in full after our runner was built (note 13). The decomposition matches ours; the one difference that matters is where the process boundary falls.

boundaryherdr owns the PTYs in its own server process, so a restart restores the layout but the agent processes do not survive. We put tmux between the runner and the processes, so an update or a rollback leaves them running. The cost is terminal fidelity: they own the emulator, so they get splits, mouse and image protocols. manifestsTheir agent detection is versioned data, one file per agent, with rules carrying a priority, a screen region and negative guards — and the terminal title as the most reliable region. We took the shape, wrote our own rules, and fixed a real bug doing it: a spinner frame is still on screen under a question that has just appeared. hooksWhere an agent exposes lifecycle hooks, those are authoritative and screen reading is the fallback. That answers our own open question about manifests. updatesTheir release manifest is the same shape as ours with an optional digest and no signature. Ours requires both, and refuses to update at all when no key is compiled in.

The architecture holds. What we take is not structure but craft: manifests as versioned data, hooks over scraping, and the terminal title as a first-class signal.

Stack

TypeScript for the web app and control plane, Go for the runner. pnpm and Turborepo monorepo. The web framework is not locked in: the recommendation is a Vite + React SPA, and Next.js used as a client app is also fine. The firm point is that the console is a real-time client over a WebSocket, so server components stay out of the session and sidebar screens. NestJS control plane with TypeORM on Postgres (from the Flama starter), a single static Go runner binary, and a shared protocol package that both languages generate from. Rejected: Python on targets (second toolchain on user machines), Electron (state must live server-side), Kubernetes (targets are pets, not cattle).

Open questions

  1. Who is the user on day one?Just us, or other developers too. Decides whether multi-tenant auth and billing land in phase 3 or phase 9.
  2. Self-hosted first, or hosted control plane?The runner model works for both. Recommendation: self-hosted via docker compose first. It keeps us honest about simplicity, which is the OpenClaw lesson.
  3. Do child sessions share the parent's workspace?Shared is simpler for "fix these three files", separate is safer for "try three approaches". Recommendation: separate by default, shared as an option.
  4. How much of Orca's cockpit to replicate?Splits, tabs, diff view, and port forwarding are essential. Monaco editor and embedded browser can wait.
  5. Name.The idea is "nation orchestrator", the repo is oppenheimer. Pick before the protocol package gets named.
