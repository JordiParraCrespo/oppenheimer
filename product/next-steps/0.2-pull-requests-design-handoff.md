# Design handoff — the Pull requests area, version 1

For a design agent (Claude Design) picking up the visual design of
Oppenheimer's Pull requests area. It is self-contained: read it top to
bottom, and you have what the product discussion settled between
2026-09-27 and 2026-10-05. The background behind it is in
[`0.2-pull-requests.md`](0.2-pull-requests.md), the brief and lanes in
[`../15-reviewing-at-agent-speed.md`](../15-reviewing-at-agent-speed.md),
and the market scan in
[`../16-developer-tools-landscape.md`](../16-developer-tools-landscape.md).
A first rough canvas exists (§9). Treat it as a sketch to improve, not a
spec to copy.

## 1. The product, in one paragraph

Oppenheimer is a browser console for running coding agents (Claude Code,
Codex) on machines the developer owns. You pair a host, start sessions,
and each session is a git worktree with a tmux terminal streamed to the
browser. Agents now open pull requests faster than people review them:
agent PRs wait about 5× longer for a first review than human ones
(LinearB, 8.1M PRs). The Pull requests area exists to **review what
matters, fast, with the context already in front of you**. It is for
people who push hard. Nothing in it slows agents down.

## 2. What version 1 is (owner, 2026-10-05)

Two things, nothing else:

1. **The PR queue, with a summary on every PR**, and fast keyboard
   triage.
2. **Analytics** for pull requests.

Everything else we discussed is later (§8). Design version 1 so those
later pieces have an obvious place to land, but do not draw them as
working.

## 3. Where it lives

- The console is one screen: a **rail** on the far left, a **sidebar**,
  and a **pane**. The rail today has *Sessions* and *Automations*.
  **Pull requests** becomes the middle item. It shows a small dot when
  there is a PR waiting on you, and that dot is the only badge.
- The Pull requests sidebar holds two places: **Queue** (the default,
  with a count) and **Analytics**. Analytics lives here, not as a global
  page, until it covers more than PRs.
- URLs: `/pulls` (Queue), `/pulls/analytics`,
  `/pulls/{owner}/{repo}/{number}` (a PR open in the pane, with the list
  kept beside it).

## 4. Screen 1 — the Queue

**The question it answers:** *what should I do now?* It lists only PRs
where it is the user's turn, not everything that is open.

**Sections**, each folding away when empty:

1. **Needs your review.** Review requested from you (directly or through
   a team), and you have not reviewed since the latest push.
2. **Your PRs, back to you.** Something on your PR is waiting on you:
   changes requested, a required check failing, a merge conflict, or a
   review thread with an unanswered reply. This includes PRs your agent
   sessions opened for you.

**Order:** within a section, the longest wait first. The wait is
measured from when it became your turn, not from when the PR was opened.

**A row shows:**

| Element | Detail |
|---------|--------|
| Repository and number | `oppenheimer #129`, muted |
| Title | One line, truncates |
| Author | `@mara`, or `session brave-heron` when one of the user's agent sessions opened it (show this distinctly: a small terminal glyph) |
| Reason | Why it is in the queue: *Review requested*, *Re-review: 2 new commits*, *Changes requested*, *CI failing*, *Conflicts*, *2 unanswered threads* |
| Checks | ✓ green, a count failing, or running |
| Size | XS ≤10, S ≤50, M ≤250, L ≤1000, XL above, counted on changed lines outside generated files. A small mono badge |
| Estimated review time | `~6 min`, from a formula. Bands: under 5 min, 5–19, 20+ |
| Chips | **type** (feat, fix, refactor, docs, chore, test, perf), **risk** (only when medium or high), **area**. See §6 |
| Wait | `5h`. Neutral, then amber at 4 working hours, red at 1 working day |

**Filters:** three chips, *Needs my review* / *Mine* / *All*, and a
repository picker. No saved views in version 1.

**Primary action:** **Start triage** (key `t`), top right.

**Empty state:** "Nothing waiting on you", plus when the oldest PR of
yours went out for review, so the empty state still says something
useful.

## 5. Screen 2 — a PR, and triage

Opening a row fills the pane with the PR and keeps the list beside it.
**Triage** is the same pane in a focused mode that walks the queue.

**Triage header:** *Triage · 2 of 7*, a small progress strip, ← back to
the Queue, and the last action with **Undo** ("Approved #127 · Undo").

**The summary** sits at the top of every PR, written by a summary agent
when the PR entered the queue and cached per commit. Its shape follows
CodeRabbit's walkthrough, which the owner shared as a reference, but
code decides the fields, not a model:

1. **Walkthrough:** two or three sentences on what the PR does and why,
   with the linked issue.
2. **Changes, in reading order:** a table of cohorts (grouped files),
   each with a one-line summary. Order is the core change first, then
   callers, then tests and copy. Code computes the order; the agent only
   writes the summaries.
3. **Facts strip:** four small cards.
   - **Type**, with its source ("from title", or "Jev 0.94").
   - **Effort**: `~6 min · S`, with lines and files.
   - **Priority**: from labels and the base branch, never guessed.
   - **Merge risk, up to `<sha>`**: Low / Medium / High, with the
     reasons (risky paths touched, auth or data changes). It is pinned
     to the head commit and marked stale when a new push lands.
4. **Checks:** required GitHub checks, green or failing, with the
   failing step.

Below the summary: **Files** (the diff; when you have reviewed before,
it defaults to *changes since your last review*) and **Conversation**.

**Actions:** a column on the right on wide screens, a bar at the bottom
on narrow ones. Each shows its key:

| Key | Action |
|-----|--------|
| `a` | Approve, and merge if allowed |
| `r` | Request changes (opens the composer) |
| `c` | Comment |
| `enter` | Open the diff |
| `s` | Skip until it gets a new push or comment |
| `o` | Open on GitHub |
| `j` / `k` | Next / previous |
| `esc` | Back to the list |

After any action, triage opens the next PR by itself. The last one ends
on "Nothing left to review".

**Acting in the user's name.** Approve, comment and merge are posted to
GitHub as the user. When GitHub will not allow the merge (a required
approval the user cannot give on their own PR, a check still running,
a code owner), the PR **waits** and says what for. Show that waiting
state clearly. No error, no workaround.

## 6. The chips, and what "algorithmic first" means visually

The owner wants this area to be **predictable**: rules decide, and an AI
model (TypeSafe's **Jev**, a classifier that returns typed answers with
a confidence) only fills gaps. The design should make that visible
without being noisy.

- A chip always carries its **source** on hover: *from title*, *from
  paths*, *from labels*, or *Jev 0.94*.
- Jev's answer shows only at **0.9 confidence or above**. Between 0.5
  and 0.9 it shows with a `?`. Below 0.5 the field reads
  **unclassified**, never "Other".
- Risk chips appear only for medium and high. Low risk is the absence
  of a chip.
- Keep it to at most three chips per row (type, risk, area). Effort
  already has its minutes.

## 7. Screen 3 — Analytics

Personal numbers about pull requests. No ranking of people, ever.

- **Header:** period picker (7 / 30 / 90 days, compared with the period
  before) and scope (all repositories, a project, a repository).
- **Weekly summary card** at the top: one or two sentences built from a
  template, not generated prose. For example: "You reviewed 14 PRs,
  median response 3 h (last week 5 h); 2 of yours waited over a day."
- **Groups:**
  - **Throughput:** opened, merged and closed per week, stacked by who
    wrote it: *your sessions*, *you*, *others*. This human/agent split is
    the one thing no other tool shows exactly, because we know which
    session opened each PR.
  - **Your reviews:** reviews given (approve / changes / comment),
    comments written, PRs reviewed.
  - **Speed:** time to first review, review to approval, approval to
    merge, total cycle time. **Median with p75**, never averages, shown
    as stages of one bar.
  - **Size:** size distribution (XS–XL), and cycle time by size.
  - **Agents:** PRs from sessions, share merged, first-push CI pass
    rate, review rounds before merge.
- **Every number is a link** to the list of PRs it counts, and every
  tile has an info hover with its exact definition.

## 8. Later — leave room, do not draw as working

- **Lanes:** Auto / Quick / Deep, chosen by Jev, each with its own agent.
- **Auto-merge** by a readable per-repository policy, proven by a dry
  run over the last 100 merged PRs, with an audit log.
- **Prepared review sessions** for Deep PRs: the PR checked out on the
  user's host, tests run, the app started, a live reviewer-agent
  terminal beside the brief, findings drafted as a pending review
  (keep / edit / drop).
- **"What it ran"** in the summary: the commands the agent ran and
  their results.
- **Saved views**, as named searches in GitHub's query syntax.
- **Make it mergeable**: one key starts a session that fixes the
  threads, failing check and conflict.
- Known-flaky tests, collision warnings, nudges, and mobile triage.

## 9. Look and feel

- **Use the existing design system**, not a new look:
  `product/versions/mvp/design/` (the version-1 export, including
  `Components.dc.html` and `SessionsConsole.dc.html`) and
  `packages/frontend/design-system/web/src/styles/globals.css`.
- **The essentials:**
  - light canvas `#ffffff`, sidebar `#fafafb`, rail `#f2f2f4`;
  - text `#1d1d1f`, muted `#6e6e73`;
  - borders `#e6e6ea` (surfaces) and `#d2d2d7` (controls);
  - one blue for actions, `#0071e3`;
  - success `#03aa49`, warning `#ed6300`, danger `#e8272c`, darkened
    when used as text;
  - radius 10 px (controls) and 14 px (panels);
  - the system font stack, with a mono stack for numbers, keys and
    paths;
  - a dark theme exists in the same file and must work.
- **Dense, calm, keyboard-first:**
  - every action shows its key;
  - no emoji;
  - no gradients;
  - at most three chips on a row;
  - colour only where it carries meaning (wait, risk, checks).
- **The first canvas** (a rough sketch from this discussion, which
  includes the later screens):
  <https://claude.ai/artifact/XZMNXi2Qq17g8mjaQyoBmq>. Its Queue, Triage
  and Analytics frames are the version-1 starting points. Its Review
  session and Auto-merge frames show §8 and are not version 1.

## 10. Questions the design should answer

1. Where does the summary sit relative to the diff: above it, as a tab,
   or in a right-hand column that stays while you scroll the files?
2. How does triage feel different from simply opening a PR: a mode with
   its own header, or the same pane with a progress strip?
3. How do the chips' sources and confidences show without making every
   row busy?
4. How do *waiting* states read ("waiting for an approval you can't
   give", "check running"), so they look like progress and not errors?
5. What do the Queue and Analytics look like on a phone? Mobile triage
   comes later, but the layout should not fight it.
6. What are the empty states: no GitHub connected, no PRs at all,
   nothing waiting on you, and Analytics before the 90-day backfill
   finishes?
