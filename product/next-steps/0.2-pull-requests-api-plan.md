# 0.2 — Pull requests: the API plan

How to build what `../versions/mvp/design/version1/PullRequests.dc.html`
draws (the 2026-10-05 evening export) in `apps/api`. **The frames are the
spec for this first version** (owner, 2026-10-05). Where this plan and
[`0.2-pull-requests.md`](0.2-pull-requests.md) or the design handoff
disagree, the frames win. Facts about today's code are from a survey of
`apps/api` on 2026-10-05; each section names the files it builds on.

## 1. What the frames ask of the API

| Frame element | Data it needs |
|---------------|---------------|
| Rail item and sidebar: **PR queue**, **Analytics**, scopes **Mine**, **Review requests**, **Watching** | Counts per scope and per lane |
| **Manage repositories** (watched repositories) | The repositories the user can push to, and which ones they watch |
| Queue header: ready to merge, with conflicts, oldest waiting, median wait, **Review next** | Aggregates over the user's open PRs |
| Queue row: lane (Quick, Medium, Deep; *Auto* as a reason), PR, size (+/−), checks, conflicts, waiting time, author (a person, or *Session · name*) | The PR projection, its lane, and whether one of our sessions opened it |
| A PR: **Brief**, with bullets (`bp`), a one-line brief, the lane's *why*, **Where it changes**, reviewers | The brief per head commit, lane and reasons, reviewers |
| **Prep** rows: *Checkout built 1m 42s*, *Affected checks 214/214*, *App started localhost:5173*, *Context pack 9 callers · 3 rules*, *Approved by you* | Steps reported by a review session on a host |
| **Findings** from the review agent (`path:line`, text) and **Pending comments** | The agent's findings, kept per head commit; the user's pending review |
| **Files**: file tree, diff hunks, *Viewed*, line comments, *Add single comment*, ⌘⏎ adds to review | Files and patches; review threads; the user's pending review on GitHub |
| **Review decision**: Approve, Approve and merge, Approve with comments, Request changes, Comment | Submitting a review in the user's name |
| **Path to merge** and the waiting notes: *needs a code owner*, *needs 2 approvals*, *2 ahead in merge queue*, *behind main by 6 commits*, conflicts | Branch rules, the merge state, the merge queue |
| **Merge** behind a confirm: "Approves and merges as Jordi Parra (@jordiparra)", "merges once required checks pass" | Approving and merging with the user's own token, or GitHub's auto-merge |
| **Terminal**: "Ask the review agent, or run a command" | The Deep review session, which is an ordinary session |
| **Analytics**: created, merged, reviewed by you, median wait for review, median time to merge (agent vs people), lane mix, auto-merged %, merged on first review, reverted after merge, agent findings you kept, opened with failing checks, PR size, **why PRs waited on GitHub** (code owner, checks, conflicts, behind) with median hold; any date range up to two years since 2023 | An event history per PR |

## 2. What exists to build on

- **`github` module.** The App installation, `GithubAppPort` over plain
  `fetch` (`infrastructure/github-rest.adapter.ts`, App JWT, API version
  2022-11-28), `RepositoryAccessPort` (`REPOSITORY_ACCESS`) as the one
  door other modules use, and repository listing cached 60 s.
- **Webhooks already arrive.** `POST /v1/github/webhook` checks the
  signature. Everything except `installation` goes to `inbound-events`:
  an `inbound_delivery` row, the INBOUND_EVENTS queue, then a normalizer
  that already maps `pull_request`, `pull_request_review`,
  `pull_request_review_comment`, `issue_comment`, `check_suite` and
  `status`. It raises `ExternalEventReceivedDomainEvent`, which
  automations listen to.
- **Automations.** A GitHub trigger, runs that dispatch
  `CreateSessionCommand` as the owner, the `pull_request_head` checkout
  rule (forks start on the default branch), and event data wrapped as
  untrusted in the prompt.
- **Sessions.** `CreateSessionCommand` with one checkout
  (`{installationId, githubRepoId, baseBranch?}`), a launch
  (`model`, `permission`, `effort`), a prompt and an origin. The working
  branch is always `oppenheimer/<slug>` cut from `baseBranch`.
- **Infrastructure.** Outbox (`outbox/`) and BullMQ with
  `upsertJobScheduler`, `CacheService`, `LlmService`
  (`packages/backend/llm`, text only), the feature-flag catalog, and
  migrations in `apps/api/src/migrations/`.
- **A pattern for stored OAuth tokens.** Plan's calendar keeps Google
  refresh tokens sealed with AES-256-GCM: `TokenSealerPort` and
  `aes-token-sealer.adapter.ts`, keyed by `CALENDAR_TOKEN_KEY`.

Missing today:

- a stored GitHub token for the user;
- PR permissions on the App;
- any PR table;
- diff, review or merge calls;
- checking out an existing PR branch in a session;
- a channel for a session to report findings.

## 3. Acting in the user's name: the user token

The frames say "Approves and merges as Jordi Parra (@jordiparra)". That
needs the user's own GitHub token, not an installation token.

- **Use the App's user access token**, from the user authorization the
  install flow already runs (`listUserInstallations(code)` exchanges it
  and throws it away today). Turn on *expiring user tokens*:
  8-hour access tokens and 6-month refresh tokens. The token's power is
  the intersection of the App's permissions and the user's own, so
  "installation is the access control" (note 09) still holds.
- **Store it** in a new `github_user_grant` table, one row per user.
  Columns:
  - `user_id`, `github_user_id`, `login`;
  - `access_token_sealed`, `refresh_token_sealed`;
  - `access_expires_at`, `refresh_expires_at`;
  - `created_at`, `updated_at`.

  Seal both tokens with the calendar's sealer pattern under a new
  `GITHUB_USER_TOKEN_KEY` (32 bytes base64, documented in the root
  `.env.example`).
- **Refresh lazily.** A `GithubUserTokenResolver` in `github/application/`
  refreshes when the access token is under 5 minutes from expiry, with a
  Redis lock per user (`CacheService.setIfAbsent`) so two requests do not
  refresh twice.
- **When there is no grant, or the refresh has expired**, every
  write endpoint returns a `GITHUB_*` problem that the console shows as
  "Reconnect GitHub", and reads fall back to installation tokens where
  they can.
- **The new door:** `GithubUserPort` (token `GITHUB_USER`) in `github/`,
  next to `REPOSITORY_ACCESS`, so the `pull-requests` module never
  touches tokens.

**App permission changes** (users see GitHub's permission-update
prompt):

- *Pull requests: read & write*
- *Checks: read*
- *Commit statuses: read*
- *Contents: read & write* (already present; merge needs it)
- *Administration: read*, only if branch rules cannot be read
  otherwise. Try the rules API with *Metadata* first.

**Webhook events to add:** `pull_request_review_thread`, `check_run`,
`merge_group`.

## 4. A new module: `pull-requests`

Scaffolded with `/scaffold-module`. It lives in
`apps/api/src/pull-requests/` and depends on:

- `github` (`REPOSITORY_ACCESS`, `GITHUB_USER`, and the new
  `GITHUB_PULLS` port below);
- `sessions` (`CreateSessionCommand`, for review sessions);
- `inbound-events` (its domain event);
- `outbox`.

The adapter that talks to GitHub stays in `github/`: a
`GithubPullsPort` (`GITHUB_PULLS`) in the same `fetch` style, with
**GraphQL for reads** and REST for writes. One GraphQL query returns a
page of PRs with `reviewDecision`, `mergeable`, `mergeStateStatus`,
`statusCheckRollup`, `reviewRequests`, `additions`, `deletions`,
`changedFiles` and `isInMergeQueue`. REST does diffs (`/pulls/{n}/files`),
reviews, comments and merge.

### 4.1 Tables

All are tenant data on `ScopedRepositoryBase`, keyed by organization.
`/design-database` sets the columns and indexes when built; the shape is:

| Table | Holds | Key |
|-------|-------|-----|
| `pull_request` | The projection of a PR: repo ids, number, node id, title, author login, `author_kind` (`person`, `session`, `bot`), `session_id` (when one of our sessions opened it), head ref and sha, base ref, state, draft, +/−, files, `merge_state`, `checks_state`, `review_decision`, `in_merge_queue`, `queue_position`, `requested_reviewers` (logins and teams), opened, merged and closed times | `(installation_id, github_repo_id, number)` unique |
| `pull_request_event` | Append-only history for analytics: opened, ready, review requested, reviewed (with state), commented, pushed, checks failed or passed, merge blocked (with reason), queued, merged, closed, reverted | `(pull_request_id, occurred_at)` |
| `pull_request_brief` | One row per PR per head commit: `lane`, `lane_reason`, `lane_source` (`policy`, `jev`, `manual`), Jev's probabilities, `auto_eligible`, `bullets[]`, `brief`, `changes` (cohorts in reading order), `status` (`pending`, `ready`, `failed`), the model used | `(pull_request_id, head_sha)` unique |
| `pull_request_review_run` | The Deep lane's prepared session: `session_id`, host, `prep_steps[]` (label, value, state), `findings[]` (path, line, text, severity), and each finding's outcome (`kept`, `edited`, `dropped`) for analytics | `(pull_request_id, head_sha)` |
| `pull_request_lane_override` | A user moving a PR to another lane | `(pull_request_id, user_id)` |
| `watched_repository` | A user's watched repositories | `(user_id, installation_id, github_repo_id)` unique |

**Pending comments get no table.** GitHub's own *pending review* is the
store: the user's draft review is created with the user token, comments
are added to it, and it is submitted with a decision. That is exactly
what the frames' *Pending comments* and *Review decision* are, and
GitHub keeps the draft if the user goes on to finish on github.com.

### 4.2 Keeping it current

1. **Webhooks.** A new `@OnEvent` handler on
   `ExternalEventReceivedDomainEvent`, filtered to PR, review, comment,
   check and merge-group events. It reads the raw payload from
   `inbound_event`, upserts `pull_request`, and appends
   `pull_request_event`. A new head sha stages a `pull-requests.brief`
   job through the outbox.
2. **A reconcile job.** A BullMQ scheduler every 5 minutes per watched
   repository: one GraphQL page of open PRs. It fixes anything a missed
   webhook left behind, and catches what GitHub sends no webhook for (a
   base branch that moved and created a conflict).
3. **Review requests outside watched repositories.** A GraphQL search
   with the user token, `is:open is:pr review-requested:@me archived:false`,
   cached 60 s. Results upsert into the same projection.
4. **Backfill for analytics.** When a repository is first watched,
   closed and merged PRs from the last 2 years are read in pages under
   the rate limit, with progress shown on Analytics. The date picker's
   floor is 2023 and its range is 2 years.

### 4.3 Lanes and the brief

On a new head commit, a `ResolveLane` application step runs:

1. **Policy first.** A default lane policy is catalog data in
   `packages/shared/src/pull-requests/lane-policy.ts`:
   - risky paths (`auth/`, `deploy/`, `migrations/`, secrets, protocol)
     go to **Deep**;
   - over 1,000 changed lines go to **Deep**;
   - a new protocol message, with no auth or migration change, goes to
     **Medium**;
   - docs, tests, formatting or CI config only, under a size limit, go
     to **Quick**.

   **Auto** is a Quick PR that also matches an auto rule: text-only
   (copy), tests only, or formatting only. "The formatter proved no
   syntax tree changed" means the runner checks it (§4.4); in this first
   version, formatting-only is decided from the diff.
2. **Jev only when the policy has no answer.** A `choice` over
   Quick / Medium / Deep, with the 0.9 gate. Below it, the PR goes one
   lane up. Jev sits behind a `LaneClassifierPort` with a rules-only
   adapter and a TypeSafe adapter, under a `TYPESAFE_API_KEY` env var.
3. **Write the reason** the frames show: "Deep by policy: touches auth/
   and changes 860 lines." or "Medium: picked by the lane policy."

**The brief for Quick and Medium PRs** (bullets, one line, changes in
reading order) is written by the API through `LlmService`. No host is
needed, and these are the majority. Code computes the reading order
and the cohorts; the model writes only the sentences. `LlmService` is
text-only today, so the call asks for JSON and validates it with a Zod
schema from `packages/shared`. If it fails, a retry, then `failed`, and
the row shows no bullets rather than wrong ones.

### 4.4 Deep: the prepared review session

The frames' Deep PR carries *Checkout built*, *Affected checks*, *App
started*, *Context pack* and findings, and its terminal is a running
session ("Review #482 …" on `mac-studio`). So a Deep review is an
ordinary session with three additions:

1. **Check out the PR's head, not a new branch.** Add to the session
   checkout schema (`packages/shared/src/schemas/session.schema.ts`) a
   `ref: { kind: 'pull_request', number, headSha }`. The runner creates
   the worktree at that commit, detached, with no `oppenheimer/<slug>`
   branch. This is a protocol change: a new field on `session.create`,
   offered under a new runner capability in `hello`, so older runners
   are not sent it.
2. **Prepare, then report.** The session starts with
   `origin: 'review'` and a prompt built from the context pack:
   - the PR, its linked issue and earlier review threads;
   - the callers of changed symbols;
   - the repository's `AGENTS.md` and `REVIEW.md`;
   - CI results.

   The runner reports prep steps and findings over the link as a new
   message, `review.report { sessionId, step | findings }`. The agent
   writes them through the runner's local CLI (`oppenheimer review step …`,
   `oppenheimer review finding path:line "…"`), and the runner forwards
   them. The terminal never has to be scraped.
3. **Starting it.** It starts on its own, as a **review automation**
   (an automation with a GitHub trigger on PRs entering the queue whose
   lane is Deep, using the agent and model picked in the automation's
   Agent step), or on demand from the PR (`POST …/review-session`).
   Either way it is `CreateSessionCommand`, idempotent per
   `(pull_request, head_sha)`.

**Security rule for this step.** A review session runs someone else's
code on the user's machine. It is prepared automatically only when:

- the PR's head is in the same repository (not a fork); and
- its author has write access.

Otherwise the PR shows *Prepare review session*, which the user must
press, with the author named. The automations module's fork rule
already points this way.

### 4.5 Reviewing, merging and waiting

Every write goes through `GithubUserPort`, as the user.

- **Line comment** (*Add single comment*): `POST /pulls/{n}/comments`.
- **Add to review** (⌘⏎): create or reuse the user's pending review
  (`POST /pulls/{n}/reviews` with no `event`), then add the comment to
  it.
- **Submit**: `POST /pulls/{n}/reviews/{id}/events` with `APPROVE`,
  `REQUEST_CHANGES` or `COMMENT`.
- **Approve and merge**: approve, then **enable GitHub's auto-merge**
  (GraphQL `enablePullRequestAutoMerge`), or enqueue it when the base
  branch uses a merge queue (`enqueuePullRequest`). GitHub then merges
  "once required checks pass", in the user's name. That is exactly the
  frames' copy, with no job of ours waiting. When the repository does
  not allow auto-merge, the API merges directly if `mergeStateStatus` is
  `CLEAN`; otherwise it records the wait and merges from the webhook
  handler when the state turns clean.
- **Merge method**: the repository's allowed methods, read once and
  cached. A squash title and body default to the PR's.
- **Waiting reasons and the path to merge** are computed, not stored:
  - from `mergeStateStatus` (`BLOCKED`, `BEHIND`, `DIRTY`, `UNSTABLE`);
  - from `reviewDecision` and the required approvals in the branch's
    rules;
  - from code-owner requirements;
  - from `isInMergeQueue` and the queue position.

  Each blocked state becomes a `pull_request_event` with its reason, so
  *why PRs waited on GitHub* and *median hold* are history, not guesses.
- **Auto lane**: when policy and brief agree and nothing is blocking,
  the API approves and enables auto-merge in the user's name, and writes
  the event. If GitHub requires an approval the user cannot give on
  their own PR, it waits, as the frames show.

### 4.6 Endpoints

All are under `/v1/pulls`, versioned, with Swagger, `@CheckPolicies` and
two new scopes in `packages/shared/src/scopes/catalog.ts`:
`pulls:read` and `pulls:write`. Commands return an id; the controller
then queries.

| Method and path | What |
|-----------------|------|
| `GET /v1/pulls?scope=mine\|requested\|watching&lane=&q=&repo=&cursor=` | The queue rows |
| `GET /v1/pulls/summary?scope=` | Counts per scope and lane, ready to merge, with conflicts, oldest waiting, median wait, and the id for *Review next* |
| `GET /v1/pulls/{repoId}/{number}` | The PR: description, brief, lane and reason, reviewers, checks, path to merge, prep steps, findings |
| `GET /v1/pulls/{repoId}/{number}/files` | Files with patches, cached per head sha |
| `GET /v1/pulls/{repoId}/{number}/threads` | Review threads and comments |
| `PUT /v1/pulls/{repoId}/{number}/viewed` | *Viewed* per file, mirrored to GitHub's viewed state |
| `POST /v1/pulls/{repoId}/{number}/comments` | A single line comment |
| `POST /v1/pulls/{repoId}/{number}/review/comments` | Add to the pending review |
| `DELETE /v1/pulls/{repoId}/{number}/review/comments/{id}` | Discard a pending comment |
| `POST /v1/pulls/{repoId}/{number}/review` | Submit: `approve`, `approve_and_merge`, `comment` or `request_changes`, with a body |
| `POST /v1/pulls/{repoId}/{number}/merge` | Merge behind the confirm, with the method |
| `PUT /v1/pulls/{repoId}/{number}/lane` | Override the lane |
| `POST /v1/pulls/{repoId}/{number}/review-session` | Prepare or open the Deep session |
| `PATCH /v1/pulls/{repoId}/{number}/findings/{id}` | Mark a finding kept, edited or dropped |
| `GET /v1/pulls/repositories` and `PUT /v1/pulls/repositories/{repoId}/watch` | Manage repositories |
| `GET /v1/pulls/analytics?from=&to=&repo=` | Every tile in one response, current and previous period |

Then `pnpm generate:api-client`, and a `pulls` module in
`packages/frontend/consumer` with its query hooks.

### 4.7 Analytics

Each tile is one SQL query over `pull_request` and `pull_request_event`
for the period and the one before it. Medians use
`percentile_cont(0.5)`.

- **Created, merged, reviewed by you:** counts.
- **Median wait for your review:** review requested to your first
  review.
- **Median time to merge:** ready to merged, split by `author_kind`
  (agent vs people).
- **Lane mix and auto-merged %:** from the brief rows and merge events.
- **Merged on first review:** one review round before merge.
- **Reverted after merge:** a later merged PR whose title or body
  reverts it (`Revert "<title>"`, "This reverts #n").
- **Agent findings you kept:** `pull_request_review_run.findings`
  outcomes.
- **Opened with failing checks:** the first check event after open.
- **PR size:** the median of +/−.
- **Why PRs waited:** blocked events grouped by reason, with the median
  hold until unblocked.

There are no precomputed tables until a query is measured slow.

## 5. Order of work

Each step is a pull request that passes `pnpm check`, `pnpm arch`,
`pnpm check:api-structure` and its tests, behind a `pull-requests`
release flag (`@RequireFlag`, with an expiry) until the last step.

| # | Slice | Gives the frames |
|---|-------|------------------|
| 1 | User grant: store, seal, refresh; `GithubUserPort`; the App's new permissions and events | "as Jordi Parra" |
| 2 | `GithubPullsPort` (GraphQL list and detail, REST files and threads); `watched_repository`; `GET` queue, summary, detail, files, threads, read live with a 60 s cache | The queue, a PR, the diff, Manage repositories |
| 3 | Writes in the user's name: comments, pending review, submit, merge, auto-merge or queue; waiting reasons and path to merge | Review decision, Merge, the waiting notes |
| 4 | `pull_request` and `pull_request_event`; webhook handler; reconcile scheduler; review-request search | Live counts, waiting times, no polling |
| 5 | Lane policy, the Jev adapter, and the Quick/Medium brief through `LlmService` | Lanes, *why*, bullets, brief |
| 6 | Deep review session: PR-head checkout (shared schema, protocol, runner), `review.report`, the review automation, the fork and author rule | Prep rows, findings, the review terminal |
| 7 | Auto lane: approve and enable auto-merge by policy | *Auto* rows that merge themselves |
| 8 | Backfill and the analytics endpoint | Analytics |

Steps 1–3 already give a working queue with review and merge. Step 6 is
the only one that touches the runner and the wire protocol.

## 6. Decisions this plan takes, to confirm

1. **Who writes the Quick/Medium brief:** the API, through `LlmService`.
   No host is needed, so every PR gets one quickly. Only Deep runs on a
   host.
2. **Auto-merge waiting is GitHub's.** Auto-merge or the merge queue,
   not a job of ours, except where the repository disables auto-merge.
3. **Findings come through the runner's CLI** and a `review.report`
   message, not by reading the terminal.
4. **Forks and outside authors are never prepared automatically** on the
   user's host.
5. **Analytics backfills 2 years,** to match the date picker.
