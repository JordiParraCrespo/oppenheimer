# 05 — The GitHub experience, end to end

Note 02 covered how the token reaches git without ever entering the
machine. This note covers everything the user actually touches, from
"connect GitHub" to "auto-fix my PR", as Claude Code on the web does it,
and what each piece costs us to replicate. Sources are the official docs
plus direct observation from inside one of its sessions.

## 1. Connect, once

1. Sign in, click **Sign in with GitHub**, approve the OAuth
   authorization. From now on sessions can reach **any repo that GitHub
   account can see**. Installing the Claude GitHub App on a repo is a
   separate, optional step that only enables PR webhooks for auto-fix and
   routine triggers. It is not access control.
2. Alternative for CLI people: `/web-setup` reads the local `gh` token
   and links it to the account. Same result, no browser. It warns if the
   token lacks the `workflow` scope, since pushes that touch Actions
   workflow files would be rejected.
3. Onboarding creates a **Default environment**: Trusted network access,
   no setup script. Environments carry network level, env vars, API
   credentials, and a setup script, and every surface (web, CLI `--cloud`,
   routines, mobile) uses the same ones.

For us: one GitHub App with both a user OAuth flow (for "what can this
person see") and installation on repos (for webhooks and scoped tokens).
Plus a `gh` token import for people who already live in the terminal.
Plus a Default environment created silently on first login.

## 2. Start a task

- Repository selector with a **branch selector** per repo. Multiple repos
  in one session.
- Permission mode dropdown: Auto, Accept edits, Plan.
- **Prefill by URL**: `claude.ai/code?prompt=...&repositories=acme/webapp&environment=...`
  so an issue tracker can deep-link into a new session with the issue as
  the prompt. `prompt_url` for long prompts.
- Provisioning shows a live checklist: clone, setup script, ready.
  Messages typed during provisioning are queued.

For us: same selector, same URL params (they are a five-minute feature
with a large payoff for integrations), and the provisioning checklist is
just the VM lifecycle from note 03 rendered as steps.

## 3. What the session sees (observed from inside)

```
remote.origin.url   = https://github.com/<owner>/<repo>
user.name           = Claude
user.email          = noreply@anthropic.com
user.signingkey     = /home/claude/.ssh/commit_signing_key.pub   (key lives outside the VM)
http.proxyauthmethod= basic
credential.interactive = false                                    (injected as GIT_CONFIG_* env)
url.https://github.com/.insteadOf = git@github.com:               (SSH remotes rewritten)
url.https://github.com/.insteadOf = ssh://git@github.com/
clone               = shallow, depth 1
branch              = claude/<task-slug>-<6-char-id>
GITHUB_TOKEN        = proxy-injected
```

Notable choices worth copying exactly:

- **Commit identity is the agent, not the user.** Commits are authored
  "Claude", with a trailer `Co-Authored-By` and a link back to the
  session. PRs and comments carry a footer "Generated by Claude Code".
  This keeps GitHub history honest about who wrote what, and it is how
  the user's GitHub identity stays on the PR (the PR is opened via the
  user's authorization) while the commits are visibly the agent's.
- **Commit signing key is outside the sandbox.** The config points at a
  public key path; signing itself happens at the proxy, the same way the
  token does. Commits show as Verified without a private key in the VM.
- **Non-interactive git.** `credential.interactive=false` so a missing
  credential fails fast instead of hanging a session on a prompt.
- **Config is injected as environment, not written to disk.** The
  `insteadOf` rewrites and credential setting arrive as `GIT_CONFIG_*`
  variables ("command line" origin in `git config --show-origin`), which
  means a repo-local or global gitconfig cannot silently override them.
- **Shallow clone by default**, with a bounded `fetch --depth=N` when
  history is needed. The git proxy caps concurrent operations (a 429 with
  Retry-After) and rejects huge pushes from stale shallow clones (413), so
  the guidance is "fetch the base branch before pushing so the pack is
  thin".

## 4. Branch and push rules

- Claude always pushes to `claude/`-prefixed branches, and those are
  always accepted.
- If the prompt asks for another branch, the push is checked first and
  refused when the branch is protected, when someone else has an open PR
  from it, or when it carries commits authored by someone other than the
  user. This is enforced platform-side, not by the agent's good manners.
- Merged PR on the working branch means new work starts a fresh branch
  from the default branch, never stacks on merged history.

For us: the same three checks live in the control plane's push policy,
evaluated by the proxy at push time using the GitHub API, because that is
the only place that can refuse a push without trusting the agent.

## 5. Review and PR

- **Diff indicator** `+42 -18` on the session opens a diff view with a
  file list. Diffs are computed from raw git blob content, so repo diff
  drivers do not apply.
- **Inline comments on the diff** queue up and are bundled into the next
  message as "at `src/auth.ts:47`, don't catch the error here". This is
  the single best interaction in the product: the user never describes a
  location in words.
- **Create PR** button: full PR, draft, or jump to GitHub's compose page
  with a generated title and body. The session stays live after the PR.
- PR creation looks for a **PR template** in the repo and mirrors its
  headings. The agent does not use `gh`; it has GitHub MCP tools scoped
  to the session's repos, which is what makes "the sandbox has no token"
  and "the agent can open PRs" both true at once.

For us: diff view is xterm-adjacent UI work, the inline-comment bundling
is a small message-composer feature, and PR creation is one control-plane
endpoint that calls the GitHub API with the session's scoped token. The
"agent opens PRs without a token" property comes from exposing a small
GitHub API surface to the agent through the proxy, exactly as the
proxy-injected token already does for `git`.

## 6. Auto-fix: subscribe a session to a PR

Observed shape of the mechanism:

- A session subscribes to a PR. Afterwards, GitHub events for that PR
  (review comments, CI failures, check-suite success) are delivered into
  the session as `<wake reason="external-event">` envelopes containing
  the event JSON, with an explicit list of which JSON keys are untrusted
  external text. An idle session is woken by the event.
- The agent then investigates and either pushes a fix, asks the user, or
  skips a duplicate. Replies on GitHub are posted under the user's
  account but labelled as Claude-authored.
- Requires the App installed on the repo (that is what gives webhooks).
- GitHub emits no webhook for "base branch advanced and now there is a
  conflict", so the docs say conflicts need a manual nudge. The harness
  compensates with a periodic self check-in.
- Two mergeability notices are synthesized by the platform, not GitHub:
  "merge conflict" and "base branch recovered".

For us: the App's webhook receiver (the small public endpoint from note
04) writes events into the session's event log, and the relay wakes the
session's agent, or in a pure terminal session, shows a banner and lets
the user paste it into the agent. Marking external text as untrusted in
the envelope is cheap and worth doing from day one.

## 7. Routines: GitHub as a trigger

- Triggers: schedule, API (`POST /fire` with a bearer token and optional
  `text`), and **GitHub events**: pull request (opened, closed, labeled,
  synchronized, ...) and release.
- PR filters: author, title, body, base branch, head branch, labels, is
  draft, is merged, with equals / contains / starts with / one of /
  regex.
- Each firing creates a fresh session that clones the repo at the default
  branch and pushes `claude/` branches. Fire-payload text arrives wrapped
  as untrusted data; the prompt must opt in to acting on it.
- Per-routine and per-account hourly caps on webhook-triggered runs.

For us: this is phase 8, and it is mostly a filter UI on top of the
webhook receiver plus a "create session from template" endpoint. The
untrusted-payload wrapping is the same envelope as section 6.

## 8. Environments

- Network levels: **Trusted** (default allowlist of package registries,
  container registries, cloud APIs, common dev domains), **Custom**
  (your domains, optionally plus the default list), **Full**, and
  **None**. Blocked requests fail with 403 and `x-deny-reason:
  host_not_allowed`. The API to Anthropic is always reachable.
- **Setup script** runs after clone, before the agent, with roughly a
  five-minute budget, and its result is cached so it does not re-run
  every session. Heavy work goes to a SessionStart hook in the background.
- **Environment variables** are visible to anyone who uses the
  environment. **API credentials** (Pro/Max) are the proxy-injected kind
  that sessions use without seeing.
- Installed tools out of the box: the list we measured in note 04.

For us: environment = network level + env vars + credentials + setup
script + base image, attached to a project. The cache is a VM snapshot
after the setup script (note 03's warm start), which is why the budget
exists.

## 9. What "the same experience" costs, by piece

| Piece | Where | Size | Phase |
|-------|-------|------|-------|
| GitHub App with user OAuth + installation, "any repo you can see" | control plane | small | 3 |
| `gh` token import (`/web-setup` equivalent) | CLI + control plane | small | 3 |
| Default environment on first login | control plane | tiny | 3 |
| Repo + branch selector, multi-repo sessions | web | small | 3 |
| Prefill URL params | web | tiny | 3 |
| Git config injection as env, agent commit identity, `insteadOf`, non-interactive | runner | small | 4 |
| Proxy-injected token and commit signing at the proxy | runner proxy | medium | 4 |
| Push policy: `claude/` always, other branches checked | proxy + control plane | small | 4 |
| Shallow clone, thin-pack guidance, concurrency cap | runner git proxy | small | 4 |
| Diff view with file list | web | medium | 5 |
| Inline diff comments bundled into next message | web | small | 5 |
| Create PR: full / draft / compose, template-aware | control plane + web | small | 5 |
| Scoped GitHub API surface for the agent (MCP-style, no token in VM) | proxy | medium | 5 |
| Webhook receiver, session subscriptions, wake envelopes with untrusted keys | control plane + relay | medium | 7 |
| Synthesized merge-conflict and base-recovered notices | control plane | small | 7 |
| Routines with GitHub triggers and PR filters | control plane + web | medium | 8 |
| Network levels with default allowlist and `x-deny-reason` | runner proxy | small | 4 |
| Setup script with cache (VM snapshot after setup) | runner hypervisor | medium | 6 |

Nothing here needs new research. It is a list of small features on top
of the three primitives already designed: the outbound runner, the
credential-injecting proxy, and the session event log.
